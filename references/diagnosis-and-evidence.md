# 诊断分流与已测证据

以下是 2026-10-18 一台 Mac 上剪映专业版 11.6.0 ARM64 的本地观察，供提出假设，不能作为其他机器的事实。原始日志、用户文件名、路径、账号和媒体不包含在此 skill。

| 现象 | 优先观察 | 可执行决策 |
|---|---|---|
| 每个新迁移工程又丢链接 | 原媒体绝对路径、已保存复合输出路径、导入模式、Resources 是否链接 | 先原生重链→复制至草稿→保存复开，再昂贵准备；第二位置原生导入核对依赖，不反复建新草稿掩盖问题 |
| 多选后没有响度控件 | 图片、已分离音频的视频等不合资格项是否混选 | 仅选真正有音频的片段/复合，直接 Audio 勾选；原生无该项就不推荐只粘贴响度 |
| 打开后一直等待 | 何时可编辑、解析/迁移栈、媒体路径访问、后台队列开始点 | 分阶段记录；先完成一次原生重链/保存复开，不重复导入成新草稿 |
| 时间线短，准备却很久 | 内部复合的实际区间与输出时长 | 减少已证明冗余的长复合工作，保留有效缓存 |
| 已保存设置后队列疑似残留 | 当前成片、原生任务身份、实际输出、前后状态；先保护必要缓存 | 证据支持残留时仅做一轮保存后的正常重开且只开目标；Home/页头计数不证明队列已重置 |
| Parallel2 两行进度一致 | 两独立物理输出/worker、每行与任务的实际映射；不要只看百分比 | 已发现本实验共享回调缺少身份筛选的适配缺口；progress 可串扰、state 也有静态风险，尚未修复；不据此判定重复渲染或精确完成 |
| 进度条静止 | 不同任务的原生状态、缓存大小/mtime/最终化变化、线程采样 | 输出持续增长时继续等待；同点无进展时补证据再恢复 |
| 弹窗打开后界面很慢 | 主线程是否反复更新任务列表 | 关闭弹窗，单独评估渲染进度 |
| 关闭响度勾选但文件仍增长 | 原生任务行、目标缓存与同组任务的变化 | 勾选关闭不代表已启动任务取消；需要停止时使用原生行取消并核对实际结果 |
| 响度显示等待 | 复合缓存与音频算法的依赖 | 读 loudness reference，按声音目标选择流程 |
| 导出面板打不开 | 原生采样是否在目录枚举/打开 | 在原生 UI 选择本地输出目录，保留系统权限策略 |
| 外置 SSD 被怀疑 | 实际读取/写入、连接模式、空间与持续负载 | 只根据所测范围判断，不凭品牌/接口标称下结论 |

本地工作工程里观察到：约 4 分 8 秒成片可能引用约 10 分 28 秒的内部复合；15 份长输出完成间隔 141–144 秒，平均 142 秒，合计相当于约 157 分钟内部媒体内容。15 份按此估算约 35.5 分钟，但不是已证实的单次冷启动任务清单。缓存累计量包含多轮运行，不可全计为当前一次消耗。

一次 1,597 样本的主线程采样中，83% 位于任务列表更新，物理占用约 10.4 GB，当时系统仍有空闲内存且无热警告。另一次小工程补丁 smoke 的 905 样本没有该路径；两者工作负载不同，不能直接算提速百分比。

短 SSD 测量：8 GiB 顺序读约 797 MB/s，平均写约 446 MB/s，写尾段约 330–360 MB/s；实际两路源素材读约 747–773 MB/s。总检查约 34 秒，不能证明一小时热稳态或硬盘健康，写回落原因未确定。不要在用户盘默认做测速；如需测，限定新建的专用临时文件、空间和数据量，只删除自己创建的文件，并说明读写缓存边界。

报告“卡住”前区分有效渲染、依赖等待、UI 主线程工作、路径/权限访问和完成文件最终化。采样中的依赖注入函数不自动证明锁死；CPU 未满也不证明有安全可调的并发余量。需要退出前先保存/快照，停止正在进行的工作应由已有授权覆盖，避免强杀丢失工程。

独立工程冷派生缓存 ABBA：相同两个约 628 秒复合，串行均值 267.869 秒，两任务均值 268.886 秒，未测到吞吐提升。两任务确实同时执行；后续单独采样主要等待在编码提交/VideoToolbox 链，支持调查下游背压这一假设，尚不能认定硬件饱和、具体等待对象或全局锁。该测试从外置盘读素材、向内置盘写派生缓存，OS 页缓存未控制；不代表所有 SSD 工程迁移。简单工程打开约 2–3 秒仅是观察，没有首次打开/解析提速对照。当前仍优先串行，并按 migration reference 的原生顺序减少重复长复合生成。


## 排队与取消时的实际操作

先把需要的区间、效果、音频设置一批定下来，让已启动的准备完成；不要因百分比或弹窗行没变化反复开关响度、退出重开。每隔合适间隔记录不同输出组的大小/mtime、最终文件出现及原生任务状态；需要标准化文件层记录时使用 [只读观测器](cache-observer.md)，不把采样计数当任务总量；视频与 alpha 只算一个复合任务。仍有物理增长或完成事件就记录进展，不能仅凭 UI 静止宣布挂死。

若确实需要停止，使用当前原生任务行的取消控件，并检查目标停止/清理、兄弟任务仍正常推进、原生状态可恢复；不要用关勾选或强杀代替已验证取消。一次场景 C 的关勾选未停止准备，原生行 X 才在下一采样看到目标文件移除，同组任务继续；稍后重试成功，详见 benchmark reference。取消全部、立即重试与长期恢复未验收，不从这个案例推断它们可靠。需要应用切换/重启时先保存并保留已有缓存与原工程，复开后确认实际复用。

导出前先确认素材完整、时间线与声音设置正确，避免临导出才批量切换高成本算法。后台输出最终化后，从原生面板选择可访问的本地目录，以新文件名导出；记录“面板可打开”“准备就绪”“最终文件完成”三个节点。读完整文件并核对规格，保存工程后再复开验证。面板目录访问、准备任务完成和完整导出是三个独立验收项。


## 受控小试与停止

后续完整迁移工程导出等待超过一小时后，用户明确取消；已保存并正常退出，没有新的最终成片。不要把此前 fixture 的成功导出当作该次交付完成，也不因后台仍有活动就延后明确取消。停止长任务优先原生取消、Save、正常 Quit，不把 Home 当作无成本 reset。

操作顺序是：先保存并保护必要素材/缓存，原生选择正确的当前时间线，确认其内层复合、音频/效果等递归必要依赖及有效缓存。精确运行时闭包尚未取得，不把库定义、全局队列或页头数当最少任务分母，也没有已实现/验证的 active-film scope 修复。只做一个有代表性的复合小试，三分钟内观察原生可操作性、作用范围、任务/输出身份与实际变化；到门槛仍不明就停止扩大范围、保留证据并诊断，不转成全片一小时轮询。三分钟不是完成 SLA，不自动取消仍在正确渲染的任务；用户显式取消随时优先。

一次复杂复合跨工程粘贴，经“原生复制→正常退出/重开→空工程粘贴”和“同进程复制→原生 Home→空工程粘贴”两条路径均未得到内容，Edit → Paste 观察为禁用。没有诊断剪贴板内容，不能推广为所有版本不支持；该路线当前未验收，不继续复制整片或反复新建工程来试。此结论不等于同一工程内复用现成子草稿必然无效，后者仍需原生入口和语义等价验证。

稳定自有派生缓存曾以本地硬链接保护，再复核 size/mtime 不变；这里只说明观察窗口的元数据保留。应用关闭后复核保护链接的 size/mtime 仍不变，但部分 owned 源目录路径已被此前原生 Home 流程移除，保护链接仍在。硬链接共享 inode，不能隔离原地写入，不是可变独立快照、独立磁盘备份或可移植工程包。先核实归属与写入状态，保留原稿；不为试验清缓存，也不把未知版本/有效性的输出盲目还原到工程。

## 共享队列、一次受控重开与最小任务数核查

本版本的静态路径显示：导出复合预编译等待使用 **EditorMode 共享 helper 的整个视频队列**，该路径没有按当前活动成片过滤。这提供了检查进程残留/共享工作影响的理由，不能据此确定某项工作是多余任务，也不证明所有队列项都不属于当前成片。

一次外置盘中断后的原生 canary：只保存并回 Home、再打开，没有减少页头计数，反而从 91 到 103。在保存/Home/复开这一原生生命周期中，41 组实验生成的 final-name 输出 family 有 32 组被应用移除；不是手动清缓存，也不能把被移除项定性为无引用或不必要。

随后保存并正常退出应用，重新打开同一工程且只打开目标成片，页头从 103 到 33；原生没有缺失项，9 个独立音频的响度 ON / -23 LUFS 完成状态保留，抽查一个已改复合仍 ON、音量 +5.9 dB、淡入淡出 0/0。对另外保留的 843 个原缓存文件，大小与 mtime 监测未变化。这是一次队列显示减少、配置保留与特定原缓存观察；不是“只需要 33 项”或所有缓存保留的证明。观察截点导出仍在 5% 准备，**没有端到端提速或该次最终导出完成证据**。

可重复使用的操作顺序：先完成并冻结重链/复制/画面/响度设置；保存并核对独立保留的原稿、必要素材和可复用缓存。只有中断后或设置稳定后，原生状态、任务身份和实际输出证据支持进程队列残留时，才安排**一次**正常退出/重开，仅打开目标成片。先盘点可能被原生生命周期回收的生成文件；运行中的目录不是一致工程快照。复开后核对缺失项、音频/复合响度、原有音量/淡入淡出与缓存变化，再观察真实进展。若没有改善或又丢必要文件，保留证据处理具体依赖；不重复 Home、重启、切开关或清缓存来追逐更小页头数。仍在有效增长的输出不因弹窗静止就判为残留。

要计算最小生成任务，先原生确认正确的活动成片，再递归追踪它引用的内层复合、有效区间、速度、混音/效果/算法和素材，按对应内容版本/设置验证缓存有效性；不透明引用仍为未知。库定义总数、全局任务数、当前页头数都不是这份依赖闭包。color 与 alpha 是一组，音频算法可能是另一个依赖。仅在输出与声音语义等价已证明时复用；不能按同源文件去重，也不能直接缩短内层响度分析区间来减少任务。

后续实测资料包含 CPU、Metal 和 VideoToolbox 工作，媒体处理确实在推进，不能将全部等待都归为任务列表/Qt。区分 UI 压力、依赖门控、真正渲染和编码背压；这些观察不支持超频或默认增加并发。

## 后续交付与音频分支的分别验收

两任务候选完成约 20 分 55 秒 H.264/AAC 原生输出并完整解码通过；保存、正常退出后复开一次约 2.202 秒，两复合响度均已完成，四份视频/alpha 缓存在约一分钟内路径、大小、纳秒 mtime 不变。这是输出可读、保存复开与有限窗口的缓存观察；没有首次打开/解析加速结论，也不覆盖长期重建或画面/声音等价。

原生分离音频的独立冷缓存样本约 5.252 秒完成响度准备且没有 video/alpha，但完整原生 OFF/OFF WAV 对照存在 PCM 差异、通道布局未知，未通过等价门槛。不要因准备快就批量改工程音轨；保持原流程，把它限于另存工程的条件实验。ON/ON、效果/混音与人工听检尚未完成，细节与操作边界见 loudness reference。

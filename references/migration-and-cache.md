# 工程导入/打开、迁移、重链与缓存复用

工程导入包括迁移元数据、打开/解析时间线、媒体关联、缓存校验与后台准备；不等同于把媒体拖入素材库。分别测量从打开到可编辑、后台队列到就绪、导出到文件完成。用当前原生状态、线程样本和文件变化区分：工程解析/恢复、路径或权限阻塞、磁盘媒体解码，以及复合/算法队列积压。任务中心显示慢可能掩盖进度，不是工程解析本身变慢的证据。

## 迁移/首次打开：先完成一轮可定位的恢复

1. 版本迁移或首次打开外来工程前，保存并正常退出当前工程，保留停止时点的完整快照；在新的自有路径恢复一份工作副本，再通过当前版本的原生打开/导入入口登记。不要反复导入成多个新草稿来碰运气。
2. 从点击原生打开/导入开始计时，分别记录“时间线可编辑”和“后台任务就绪”。如果界面未就绪，先看原生线程样本与路径访问，判断处于元数据迁移/解析、目录/权限等待，还是已经在做复合/算法准备。任务弹窗的处理计数不代表解析进度；关闭弹窗后仍用物理缓存和原生任务状态判断。
3. 缺失素材用原生重链入口修复：可按共同目录定位一批，再逐一核对文件类型、时长/画面与图片层，避免同名文件误配。确认时间线、内层复合、音频与静态图都正确后保存；不要每次打开都重新重链已保存的映射。
4. 复开工作副本，核对实际媒体/缓存路径和命中，记录是否又开始生成相同长复合。可编辑但还在排后台任务时，按下面的工作量与缓存流程处理，不重建工程。若始终卡在同一解析/访问点，保留工程与采样，针对该点恢复；重启前先保存，避免为了刷新弹窗丢掉正在完成的缓存。

这个流程帮助避免重复迁移与重复准备，尚没有证明工程首次打开/时间线解析本身更快。简单测试工程一次约 2–3 秒可打开的观察不代表大型迁移工程，也不构成补丁对照基准。

先复用已保存且验证过的工作工程。避免每次尝试都建新草稿、重复导入/重链，或反复重启导致迁移/缓存重建。需要重启时先正常保存，记录媒体和缓存引用，复开后检查是否真正复用；若相同内容持续重新生成，先查缓存身份、物理路径和变更触发，不要继续盲目重试。

迁移导致的素材丢失、媒体权限和缓存缺失是三件事。先盘点工程元数据引用的源文件、图片、字体、插件与外部资源；用原生编辑器重链并保存，抽查开头、中间、结尾和容易漏掉的静态图层。源文件存在不等于工程已经引用正确路径。不要只因视频轨恢复就宣布全部素材恢复。

缓存拓扑也需要盘点。工程的 `Resources` 可能是链接到另一个目录的 symlink；复制工程目录可能仍共享旧缓存。读 `lstat`/`readlink` 并解析路径，确认副本真正拥有哪些目录。写、移动、重命名或删除前，必须证明 resolved path 属于本次测试；不能仅凭路径字符串看起来位于新工程内就判断安全。保存快照时记录链接，不能只比较几个 JSON 哈希后称整个工程隔离。

生产恢复优先保留已完成的复合视频、alpha 和响度缓存。迁移时检查缓存文件是否完整可读以及原生程序是否真正命中；一份视频与对应 alpha 是同一复合任务的输出组。不要为了“排障”清掉全部缓存重来。系统重启、应用重启和每轮复制工程也不应默认清缓存。

同源长复合片段可能重复准备整段媒体。仅在图像/声音合成等价已证明时考虑复用或归并：比较有效区间、速度、变换、裁切、混音、音量、效果、算法状态、输出规格和缓存身份。对象 ID 或名字相同/不同都不是等价证明；库里存在 11 份定义也不等于当前导出必须执行 11 个任务。先在另存工程由原生应用验证，再评估是否减少工作量。

## 每个新迁移工程都丢链接：先修迁移依赖，再谈缓存提速

| 迁移方式/引用 | 能保留什么、还要核实什么 |
|---|---|
| Finder 拷贝原始草稿目录 | 复制文件不自动重写工程里的外部绝对路径；旧机器图片路径、源视频路径和已保存复合输出路径可能仍指向旧位置 |
| 原生导入选择“保留原有位置” | 不能把该模式当作把所有媒体收集到新工程内；保存后检查实际解析到的路径，源目录/磁盘变化仍可能造成缺失 |
| 草稿参数改为“复制至草稿” | 本地原生实测能把两条源 MOV 收集为真实 `Resources/local` 文件，源文件保留且逐文件 SHA-256 一致；仍要逐项核对其他素材、生成输出和保存复开，不能推断所有缺失已修复 |
| `Resources` 是符号链接 | 拷目录可能只带走链接，真实缓存仍在原工程；新目录存在不代表媒体/缓存随迁移，先核对物理路径 |
| 原生工程打包/导出、`.jypack` / `.jyproj` | 与原始目录拷贝不同；按当前版本实际原生入口核实类型与收集选项。扩展名不证明自包含，不能承诺包内已有全部原媒体、图片、子草稿和有效缓存 |

**一个可持续复用的迁移顺序：**

1. 在工作副本先原生重链到确切的源视频、图片和必要媒体，核对同名异内容文件；再按下面的已验证原生入口选择“复制至草稿”，等待收集完成，检查真实本地文件并保存复开。**先重链 → 收集/复制 → 保存复开 → 再启用昂贵准备/响度与导出**，不要每建新工程继续指向旧机或临时路径，也不要在已有队列中反复改变来源。
2. 在缺失列表中分开处理**原素材**与**生成 MP4/复合输出**。对缺失复合用原生双击进入内层，核对源轨、区间、字幕/图片、音频和效果。内层仍完好时，缺失的外部输出不等于复合被压平成普通视频；保留现有源轨和有效缓存，观察原生生成/路径更新后再保存。不要用任意同名 MP4、单条源视频或别的工程缓存去顶替复合。若生成视频本来就作为独立媒体使用，它也是迁移依赖，不能当临时缓存删掉。
3. 核对实际源路径、已保存复合输出路径与 Resources 拓扑。某些输出完成、其他输出还在增长时，按身份逐组记录，不把整个工程认定为失败，也不清空全部缓存。原始素材修复与复合缓存再生成可以处于不同阶段。
4. 先保存、正常退出并复开这份修复工程，确认缺失项、复合内层和声音均正确，缓存路径实际落在预期位置。再用本版本支持的原生打包/工程导出流程制作迁移交付，逐项核对收集选项；仅提供原始文件夹时，连同已验证依赖一起交付并记录外部依赖。
5. 在**新的第二份目录/目标卷，最好实际目标 Mac** 原生导入该交付，重新核对图片、源轨、复合输出及音频，保存复开并做小范围导出。原工程、原素材与原缓存保持不动。同机第二副本如果还能访问原路径，单凭“不再弹缺失”仍不能证明包自包含；检查解析后的引用，无法读到的加密/不透明引用标为未验证，不能宣称永久修复。

### 已验证的“复制至草稿”原生入口

在编辑器点击空白处取消片段选择，找到 **草稿参数 → 修改 → 导入素材 → 复制至草稿 → 保存**；以当前原生 UI 实际可见项为准。出现“正在移动素材”进度时等待结束，不中途退出或删除源文件；结束后右侧应显示 **导入方式：复制至草稿**。再核对 `Resources/local` 是真实目录、包含预期原素材，源文件仍存在，必要时在非计时阶段逐文件比对哈希，保存并正常复开验证引用。这个设置不替代原始缺失项的重链，也不自动证明子草稿输出与所有图片已经收集。

**这是项目级设置，不是已验证的全局默认。** 本版本的原生调用路径中，`getCopyMaterial` 读取当前草稿的 `Config.material_save_mode`，`setCopyMaterial` 修改并保存当前工程；该路径没有写入 `GlobalSetting`。不能据此宣称以后新建工程自动启用，也不要编造全局开关。新建空白草稿的实际默认 UI 尚未验证，不能反向声称默认总是关闭。

因此**每一个新建或克隆的草稿**都要在昂贵准备之前检查 **草稿参数 → 修改 → 导入素材 → 复制至草稿 → 保存**；已是正确值时确认并保存，不反复切换。物理文件已经复制且哈希一致，仍可能同时存在未更新的旧引用。逐项通过原生界面验证实际素材/图片/复合输出引用与完整访问路径，保存、正常退出并复开后再核对，不能只凭 `Resources/local` 里有文件宣布链接修好。

本机一次实测原生进度显示 5,382.5 MB；完成后两条源 MOV 的草稿内副本与对应源文件 SHA-256 各自一致，源文件仍在、没有符号链接。仅这两条源素材收集已验证；没有据此认定全部 25 项缺失或原生打包依赖已修好。

这次操作发生在冷准备已运行之后：改动来源路径后任务页头计数从 31 变为 101，并出现新的算法/预合成任务。页头数不是同时活动的任务数，这也不是提速证据；它说明迁移收集与昂贵准备应分阶段安排。后续从一开始先完成重链、复制、保存复开，再一次确定响度/效果设置，避免重复队列与缓存失效。

一次真实迁移的原生缺失列表有 25 项，含旧机 PNG 引用和生成 MP4。原生双击一个实际缺失复合后，内层仍有两条完好的原始 MOV 源轨；这排除了“看到生成 MP4 缺失就认定该复合已经压平”的推断。当时已有两组 color+alpha 完成、另两组仍在生成，是部分恢复/继续准备的观察，不是全部失败或全部恢复，更不是允许盲目清缓存的依据。

“此工程当前可打开”“修复后保存复开保持链接”和“迁移交付在第二位置/机器依赖完整”是三个验收项。只有最后一项通过，才能把对应的迁移流程作为后续新工程的固定做法；尚未验证原生包全收集时，明确保留这一限制。

## 减少复合生成量：按这个顺序编辑

**新剪辑，适合只用长素材中的少量区间时：**

1. 先在原生时间线上确定需要的源区间，分割并修剪各源片段，再选择这些已裁好的片段创建复合。为转场、淡入淡出和后续微调保留实际需要的余量。不要先把整段长素材做成复合，再只裁外层的几秒；外层短不证明内部缓存也只生成几秒。
2. 多处确实需要同一套内容时，先建立并核对一个复合/子草稿，再从原生复合素材或子草稿入口把**同一已建立项**放入其他位置；避免对同一组源片段反复执行“创建复合”而得到互不共享的新定义。普通复制粘贴是否仍引用同一子草稿须按当前版本核实，不能只看名字。共享子草稿的内部修改会影响所有引用；需要不同画面或声音处理的用途应保留独立版本。
3. 一批确定画面区间、速度、效果与音频设置，预览确认后再集中做高成本预合成/响度准备。排队时先让这一批结束，避免来回切换设置反复使缓存失效。已有正确缓存继续使用，下一轮只处理实际改变的内容。

**已有工程，适合发现多个长复合疑似重复时：**先保存原工程，一次建立原生另存的可回退测试工程并保留有效缓存。只选一组疑似重复项，在原生界面查看内层范围和设置，再试缩短内层、合并或用同一已建立复合替换。对照修改前后的时间线位置/总时长、源/目标区间、转场、画面变换/效果，以及音量、混音、淡入淡出、变速和声画同步；小范围导出并看听，保存复开后核对，再扩大到其他项。出现差异就撤销该组，使用原工程继续，不批量改 ID 或缓存文件。

使用同一个输入文件不等于渲染结果相同：区间、轨道叠加、效果、速度或音频处理任一不同，都可能需要独立输出。复用后仍检查原生任务与输出是否实际减少，缓存是否命中；仅“复合数量变少”不能证明更快或等价。

最低交付检查：全部媒体可定位、编辑器不再报缺失、时间线关键位置正确、保存后复开、输出文件完整可读。用户已有官方导出与原工程时，保留它们；新验证文件使用新名称，避免覆盖。


## 从完整快照恢复到新的自有路径

先在原生应用保存并正常退出，确认没有进程继续写目标工程，再制作**同一停止时点的整份草稿快照**。把草稿元数据、加密内容及配套 crypto/密钥材料、subdraft 定义、素材映射和已有 Resources/派生缓存作为一个相互关联的集合保存；加密文件按原字节保留。只恢复几份 JSON 或混用不同保存时点的子草稿/加密数据可能不可打开，也可能强制重建缓存。

恢复时创建全新的、明确归本次恢复所有的目录，完整复制/克隆快照并核对文件清单与哈希；保留扩展属性、链接拓扑及所需元数据。不得覆盖原草稿或在其目录内试修。符号链接若仍指向原工程/原缓存，不能称副本独立：先记录解析后的目标，保留原链接和备份；需要独立可写缓存时把对应数据复制到新自有目录，再通过已验证的原生路径调整处理，不沿链接写原目录。

使用原生应用打开/导入这个新副本，核对时间线、字幕、图片、声音、内层复合和素材引用；缺失项通过原生重链修复并另存。不要为“让它认缓存”随意改工程/素材哈希、对象 ID、缓存文件名或加密元数据，也不拼接其他工程的缓存身份。若应用不支持直接在该位置打开，使用原生导入/恢复流程注册副本；保留失败现场，不编辑未知加密字段强行登记。

缓存文件存在不代表命中。复开后记录实际引用路径、原生任务状态与派生输出的 mtime/大小，确认既有缓存被消费而没有对相同内容重新生成；必要时在独立副本上做一次小范围预览/导出并完整读取输出。确认保存后再复开一次，才把恢复称为可继续工作。原快照、原草稿与原缓存全程保留；未证明命中时明确报告“恢复可打开，但缓存复用未验证”。


本轮两任务候选的一个已保存测试工程原生复开约 2.202 秒，两份复合显示响度完成，四份视频/alpha 文件在约一分钟内路径、大小与纳秒 mtime 不变。这个例子说明复开后可以检查具体缓存是否被重写；不能据此省略自己工程的路径/命中核对，也不能声称首次解析加速或所有缓存长期不重建。
